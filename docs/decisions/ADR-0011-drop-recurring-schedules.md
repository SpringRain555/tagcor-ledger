# ADR-0011：移除定期收支，模板就夠了

- 狀態：**已接受**
- 日期：2026-08-23
- 取代：無。**與 [ADR-0006](ADR-0006-manual-entry-only.md) 同向** —— 那份決定
  「每一筆都手動輸入」，這一份把最後一個帶有「自動」味道的東西也拿掉了。

## 背景

「定期收支」（schema 上是 `recurring_schedules`）讓使用者登記「每 N 個月重複這一筆」，
程式在到期時產生一筆**待確認草稿**，由使用者確認才成為交易。它從 Phase 2 就存在。

它與模板的差別**只有一項**：到期那天會主動在側邊欄跳一個待確認數字提醒你。
其餘每一件事模板都做得到 —— 兩者的欄位形狀一模一樣（名稱、流向、帳戶、類別、
金額、備註），連驗證規則都共用同一份 `validate_draft()`。

使用者的原話是「簡訊通知訂閱類項目訊息（或刷郵局簿子）的時候再登記就好」。
**他的觸發點在程式外面**，所以那個唯一的差異對他沒有作用。

### 順帶澄清兩個誤解

- **它不連網。** `today_taipei()` 讀的是本機系統時鐘，App 從來沒有發出過網路請求。
- **它不是純手動。** 除了兩顆按鈕，`ControllerBase._run_startup_tasks()` 每次開程式
  都會產生一次。不過產生出來的一律是草稿，**不會自己入帳**。

## 決定

**整個移除**：UI、controller、application、store、以及 schema 上的兩張表。

| 拿掉的東西 | |
|---|---|
| 資料表 | `recurring_schedules`、`scheduled_occurrences`（`migrate_v8` DROP）|
| store | `ScheduleStore`、`OccurrenceStore` |
| application | `AutomationService` 的排程與待確認一半 |
| UI | 「操作設定 → 定期收支」分頁、`RecurringPage` |
| 錯誤碼 | `SCHEDULE_*`、`OCCURRENCE_*` |

### 待確認**留著**，因為定存還在餵它

定存到期、每月領息、零存整付的每月存入，三者都會產生待確認草稿，而且
**實際金額要照存摺填**（試算值只是建議）。那個提醒與定期收支的不同：
**定存到期是銀行那一端自己會動的錢，沒有人會通知你。**

只剩一個來源之後，待確認頁跟著瘦身：

| 消失的東西 | 為什麼它是定期收支獨有的 |
|---|---|
| 「來源」欄 | 只剩一種來源，每一列印同一個字 |
| 「全部確認」 | `batch_confirm_valid()` 只處理定期收支。**定存刻意不批次** —— 批次套用試算值等於替使用者決定一個他沒看過的數字 |
| 「繼續產生」與漏期提示 | 「一次最多 366 期」是排程獨有的上限。定存只看未來 7 天，一次做完而且冪等 |
| `InboxEditDialog` | 它編的是 `scheduled_occurrences`。定存只問一個實際金額 |
| 「狀態說明」欄 | 對定存永遠是同一句話，改成表格上方講一次 |

**頁面名稱不改。** 「待確認」問的是「有哪些草稿等我確認」，今天剛好只由定存供應；
改成「定存到期」等於把頁面的身分綁在目前唯一的來源上。

### schema 真的砍掉，不是留著不用

使用者的帳本兩張表都是 0 筆，所以不會失去任何東西。留著不 DROP 的代價是
schema 裡永遠有兩張沒有任何程式碼會碰的表 —— 而這個專案剛剛才因為
「看不見的封存模板擋住帳戶刪除」吃過一次虧（見 [changelog 0.22.0](../changelog.md)）。

**交易本身完全不受影響。** `scheduled_occurrences.confirmed_transaction_id` 是
從 occurrence 指向 `transactions` 的，沒有任何東西反過來指向這兩張表。
失去的只有「這筆交易是從哪一筆定期收支來的」這條線索。

## 被否決的替代方案

| 方案 | 為什麼否決 |
|---|---|
| **保留，只拿掉啟動時自動產生** | 定期收支就失去它存在的唯一理由（提醒），變成一個「需要你先想到它」的提醒器 |
| **只從 UI 拿掉，schema 留著** | 違反這個專案「不留死程式」的紀律，而且看不見的東西回來咬人這件事剛發生過 |
| **把定存也一起拿掉，待確認整頁消失** | 定存到期是銀行端自己會動的錢，而且利息要照存摺填 —— 那個提醒是真的有用的。REQ-0007 那一整套（三種計息 × 四種到期轉存）也會跟著不見 |

## 後果

- **好的**：少兩張表、少兩個 store、少一個分頁、少 12 個錯誤碼；待確認頁從
  「兩種形狀合成一張表 ＋ 依來源分派」變成一張四欄的表加兩顆按鈕。
  `application/automation.py` 改名為 `templates.py` —— 這個專案裡已經沒有「自動化」了。
- **壞的**：真的要「每月房租提醒我」時沒有東西可用。使用者知情且接受，
  因為他的觸發點是簡訊與存摺。
- **要改變這個取捨就新增一份 ADR 推翻這一份**，不要順手把表加回去。
  加回來的成本不只是兩張表 —— 待確認頁的「來源」欄、分派與批次確認都要一起回來。

## 2026-08-23 當天就重新問過一次：訂閱項目要不要讓它回來？

移除之後使用者立刻回頭問：「既然看時間是用本機時間，你會建議把定期收支加回來嗎？
目前會用到的只有 LLM 訂閱，每個月 3 筆。」**結論是不加。** 理由留在這裡，
因為同一個問題半年後一定會再被問一次。

**本機時間從來不是那個決定因素。** 使用者是在知道「它不連網」之後才決定移除的；
真正的判準是他自己說的「簡訊通知的時候再登記就好」。那一句到今天仍然成立。

**而且對 LLM 訂閱這個用途，定期收支的日期是錯的。** 舊的 `confirm_occurrence()`
寫死 `occurred_at = f"{row['due_date']}T12:00:00+08:00"` —— 交易日期是**排定日**
不是實際扣款日，而確認對話框只有帳戶／類別／項目／金額／備註，**沒有日期欄位**。
LLM 訂閱剛好兩件事都會偏：USD 計價所以 TWD 金額每月不同，實際入帳日又常晚一兩天。

兩條路實際走起來，**模板的步驟嚴格比較少**：

| | 步驟 |
|---|---|
| 模板 | 簡訊 → 開程式 → 填入記帳頁 → 改金額 →（日期欄就在那裡，預設今天）→ 儲存 |
| 定期收支 | 徽章 → 待確認 → 確認入帳 → 改金額 → 儲存 → **再到交易紀錄編輯那一筆改日期** |

**定期收支省的不是輸入，是「想起來」** —— 兩條路都要開程式、挑東西、確認金額、按儲存。
而「想起來」這件事已經由簡訊負責了。

### 什麼情況下這份 ADR 該被推翻

- 訂閱長到十幾筆、扣款日散在整個月 —— 那時「這個月還有哪幾筆沒記」真的需要一份清單。
- 出現**金額固定不變的 TWD 定期扣款**（房租、保費）—— 草稿的金額與日期都會是對的，
  確認一下就好，那才是定期收支發揮的地方。

**3 筆 USD 訂閱兩條都不符合。** 真的要加回來，記得 migration 不能「un-drop」，
要新增 v9 重建兩張表，並且新增一份 ADR 推翻這一份。

### 如果只是擔心「會不會忘記」

便宜的做法**不是**把兩張表加回來，而是在資產總覽的「待辦」加一行 —— 那一區已經有
三種提醒（待確認筆數、今天沒盤點、未解釋差額），多一種「這個月還沒記過某個類別」
不需要任何新資料表。**但先用模板記兩三個月再說** —— 真的漏過，那時才會知道漏的是
哪一種情況。

## 一併補上的東西

移除定期收支之後，**定存的待確認項目就沒有手動觸發的入口了**（以前混在
定期收支頁那顆「產生到期待確認項目」裡）。所以定存頁補上
**「產生到期與領息項目」** —— README 從以前就寫著這顆按鈕存在，而程式裡一直沒有。

# ADR-0020：App 試算綜所稅 —— 推翻「不計算稅額」，以護欄回應「算錯比不算更糟」

- 狀態：**已接受**（使用者 2026-11-08 選定，知情推翻）
- 日期：2026-11-09
- 取代：[REQ-0008](../requirements/REQ-0008-reference-db.md) 邊界中「**App 不計算稅額**」那一句，
  **範圍僅限 [REQ-0011](../requirements/REQ-0011-tax-reminders-and-estimate.md) 定義的綜所稅試算**。
  同一句後半「不做申報、不依法規自動調整任何帳務數字」照舊成立。
- 相關：[ADR-0007](ADR-0007-time-deposit-modelling.md)（算出來的是建議值，不是權威值）、
  [ADR-0005](ADR-0005-reference-db-offline.md)（App 不連網）

## 背景

REQ-0008 把法規庫定位成「只是查閱用」，理由寫在 `reference/README.md`：「法規會改，而被自動調整過的帳
沒有人看得懂當初為什麼是那個數字。」ADR-0007 與市場調查（`docs/research/market-scan.md`）更直接：
**「算錯比不算更糟 —— 使用者會相信一個錯的數字。」**

使用者要稅務「有實際作用」。2026-11-08 給了四種深度讓使用者選：

| | 會說什麼 | 好處 | 代價 |
|---|---|---|---|
| 只做行事曆提醒 | 「該報稅了」 | 不會說錯 | 帳本的資料完全沒用到 |
| 只判斷要不要申報 | 「超過免申報門檻，需要申報」 | 只用兩個公告數字 | 回答不了「要不要繳錢」 |
| 要不要申報＋可能要不要繳 | 「需要申報；扣除後淨額 ≤ 0，應不用繳」 | 不給會被當真的金額 | 仍要歸類 |
| **加上稅額試算** | 「估計應補 2,700 元」 | 一眼看到金額 | 帳本是淨額、沒有扣繳憑單，金額可能錯 |

**使用者選了最後一種**，並說明：試算可能會有問題，但會越改越好。這份 ADR 記下那個選擇，
以及讓它「越改越好」而不是「一直錯下去」所需要的護欄。

## 決定

**App 依帳本與使用者填的申報狀況，估計綜所稅應納稅額與應補（退）稅額。** 計算是固定的程式邏輯，
數字來自 `reference/tax/dataset.json`；**App 不接 LLM、不用 RAG、不連網**。

護欄（每一條都是對「算錯比不算更糟」的回應）：

1. **只支援一種形狀：自己單獨申報。** 可加受扶養人數與 70 歲以上；標準扣除、薪資與儲蓄投資特別扣除、基本生活費差額。
   使用者的收入種類（薪資、利息、競賽獎金、稿費講演、免稅的獎助學金、海外所得）各有明確處理方式（REQ-0011 §所得類別）。
2. **算不準就不算。** 配偶、被他人扶養、列舉扣除、其他特別扣除、不支援的所得、稿費講演超過免稅上限、海外所得達門檻、
   可能適用最低稅負、有未歸類的收入、參數缺 —— 任何一項成立，**畫面上不出現任何稅額**，只列原因與「請改用財政部稅額試算」。
   一個被拒絕的試算是正確的；一個硬算出來的數字不是。
3. **每個數字都說得出從哪來。** 明細的每一行標「帳本 N 筆」「扣繳憑單（你填的）」「財政部公告（來源）」或「計算」；
   dataset 的每個值都帶出處 id，出處有網址、抓取時間與 SHA-256。
4. **永遠標「估計」，官方為準。** 固定說明，緊接在試算的狀態行下面、不必捲動就看得到：「這是估計，不是申報；以財政部稅額試算為準；
   不會改動帳本任何金額。」（2026-11-10：原寫「固定頁尾」，實作時頁尾會被明細表推出畫面，所以移上來。）
5. **不碰帳。** 試算結果不寫進任何帳務表、不產生交易或草稿、不申報。它只是一張算給你看的明細。
6. **帳本的缺口用手填補，不用猜。** 帳本記實領淨額 → 薪資、利息、競賽獎金、稿費講演可以手填扣繳憑單的給付總額與扣繳稅額；
   定存利息的扣繳由待確認記下來。只用帳本時明說「帳本是實領，通常低於給付總額」。
7. **對答案，讓錯誤看得見。** 申報後填財政部算出的稅額，App 顯示差多少；年度複查把反覆出現的差異原因變成規格與測試。
   這是「越改越好」能成立的前提：看不見的錯誤不會被改掉。
8. **用官方範例守住正確性。** 除了手算的黃金案例，上線前加入 1–3 個財政部公布的計算範例，要求逐元重現。

## 被否決的替代方案

| 方案 | 為什麼否決 |
|---|---|
| **維持 REQ-0008，只做提醒或判斷** | 使用者明確選了試算；而且「要不要繳、大概多少」正是報稅季最想知道的事 |
| **完整的稅額計算（配偶、列舉、股利…）** | 帳本沒有那些資料，硬做就是用猜的數字算出精確的樣子；先把一種形狀做對，再依對答案的結果擴充 |
| **讓 LLM 在 App 裡算或解釋** | App 不連網是核心不變量（ADR-0005）；而且同一份輸入要得到同一個結果，才寫得成測試、才對得了答案 |
| **把稅率與級距寫在程式裡** | 每年公告都要改程式、發版；數字放 dataset 帶出處，程式只認規則的形狀 |
| **試算結果自動記成一筆應付稅款** | 違反 ADR-0006（一律手動輸入）與「不依法規自動調整帳務數字」 |

## 後果

- **好的**：報稅季開程式就看得到「估計應補／應退多少、為什麼」；不支援的情況也說得清楚為什麼不算。
- **壞的**：多了一套要維護的規則與年度資料；歸類錯、扣繳沒填，試算就錯 —— 對答案與明細是抓這種錯的地方，
  但抓不抓得到取決於使用者有沒有填官方結果。
- `README.md`、`reference/README.md`、`REQ-0008` 裡「不計算稅額」的說法要改成指向這一份（只改現況描述，不改 changelog 的歷史）。
- 「算錯比不算更糟」這條原則**沒有被丟掉**：它從「不算」變成「算不準就不算」（護欄 2）。

## 什麼情況下這份 ADR 該被推翻

- 連續兩個申報季，對答案的差額有一半以上找不到原因、或原因修不掉 —— 那表示這種形狀的試算在這本帳上做不準，
  應該退回「要不要申報＋可能要不要繳」，並新增一份 ADR。
- 財政部的稅額試算服務變得隨時可用且比這裡準（例如年度中就能試算）—— 那時這裡的試算只剩重複，可以拿掉。

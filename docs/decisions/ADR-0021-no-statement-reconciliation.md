# ADR-0021：不做逐筆對帳；拿掉為它保留的兩樣東西

- 狀態：**已接受**
- 日期：2026-11-16
- 結案：[REQ-0010](../requirements/REQ-0010-reconciliation-gap.md) 排在 2026-10 月底的重新評估

## 背景

REQ-0010 記下的缺口：盤點只能對總額；有存摺的帳戶本來可以逐筆核對，卻沒有地方記「這一筆對過了」。
它刻意沒做，排在 2026-10 月底、實際用兩個月之後，依三個問題重新評估：差額不為零時用眼睛找不找得出來、
有沒有發生過「以為對過其實沒有」、現金帳戶的差額有多大。

為那個設計保留了兩樣東西：`EntryType.ADJUSTMENT`（「把差額轉成調整交易」那顆按鈕）與
`accounts.account_type`（「郵局能逐筆核對、現金只能盤點」的區分）。兩者從 v1 就在、從沒有人用過，
2026-08-22 起由 `tests/unit/test_reserved_schema.py` 鎖住「保持沒有人用」，並約好**兩種結論都會讓它們消失**。

評估拖過了期限，2026-11-16 才處理。**使用者判定以「沒有問題」結案，沒有逐題回答那三個問題** ——
照實記下，免得日後被讀成「三題都答過、答案是不需要」。

## 決定

**不做逐筆對帳。** 照 REQ-0010 的約定拿掉兩個保留物（v0.29.0，schema v15）：

| 東西 | 怎麼拿掉 |
|---|---|
| `accounts.account_type` | `migrate_v15` 用 `DROP COLUMN` 拿掉 —— 沒有索引、外鍵、CHECK 引用它，每一列都是 `cash`。store、application、預設帳戶的種子跟著拿掉 |
| `EntryType.ADJUSTMENT` | 列舉與兩張顯示名稱表拿掉。**`transactions.entry_type` 的 CHECK 留著 `adjustment`**：拿掉要重建整張表，與 [ADR-0015](ADR-0015-delete-balance-snapshots-for-real.md)／[ADR-0017](ADR-0017-delete-transactions-for-real.md) 留下 `status` 那條 CHECK 是同一個取捨。`tests/unit/test_retired_schema_values.py` 守著「程式不寫它」 |
| `tests/unit/test_reserved_schema.py` | 刪掉（它的 docstring 約好的）。接手的是 `tests/integration/test_reserved_fields_removed.py`：那一欄不在、流向只有三種 |

## 被否決的替代方案

| 方案 | 為什麼否決 |
|---|---|
| **繼續保留，延後再評估** | 它們保留的唯一理由是「十月就要評估」。過了期限還留著，就是 REQ-0010 自己批評的「先加著以後再說」 |
| **連 CHECK 一起拿掉（重建 `transactions`）** | posting、配置、FTS、定存事件與稽核都指著那張表；重建的風險遠大於「允許集合小一號」的好處 |
| **只拿掉程式那一側，欄位留在 schema** | 留著不會壞，所以永遠不會有人發現它已經沒有人讀 —— `migrate_v11` 刪掉那一列設定的同一個理由（ADR-0014） |

## 後果

- **好的**：schema 與程式不再帶著一個沒有人在等的設計；`accounts` 少一欄永遠是 `cash` 的值。
- **壞的**：日後真的要逐筆對帳，要重新加欄位（新的 migration）。REQ-0010 的設計與市場調查仍然可用，
  加回來的成本它自己估過（〈為什麼現在不做〉第四點）。
- **升級前要先手動備份**：`migrate_v15` 拿掉的那一欄回不來（雖然每一列都是同一個值），而程式依規定不自動備份。
- 對帳本身的需要沒有消失：總額由餘額盤點對（REQ-0003），對不上時用眼睛對存摺。

## 什麼情況下這份 ADR 該被推翻

**用眼睛對存摺不夠用了** —— 差額找不出來、找太久，或發生過「以為對過其實沒有」（REQ-0010 原本的三個問題）。
那時照 REQ-0010 的設計做：交易加「已核對」、帳戶分出有沒有對帳依據、差額轉成調整交易做成一顆明確的按鈕。

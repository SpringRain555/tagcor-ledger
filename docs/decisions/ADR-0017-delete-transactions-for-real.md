# ADR-0017：交易的「刪除」改成真的移除

- 狀態：**已接受**
- 日期：2026-10-09
- 取代：[state-machines.md](../architecture/state-machines.md) §1 原本的「刪除＝`void`，紀錄保留」，
  以及 [ADR-0015](ADR-0015-delete-balance-snapshots-for-real.md)「後果」裡「交易的刪除沒有跟著改」那一條。

## 背景

使用者問：「交易紀錄的刪除，是否為真的刪除？」答案是否 —— 交易的「刪除」是 `void`：標成已刪除、
不再計入、紀錄留著，在交易紀錄的狀態篩選選「已刪除」看得到，**不可復原**。理由寫在 state-machines.md §1：
「復原會讓『這筆到底有沒有計入』的歷史變得無法追溯。」

交給使用者決定時用的比較：

| | 維持作廢 | 改成真的刪除 |
|---|---|---|
| 誤刪之後 | 在「已刪除」裡看得到內容，可以照著重記 | 只能從備份救 |
| 只被已刪除交易用過的帳戶／類別 | **永遠刪不掉**、只能封存，訊息還說「已經有交易紀錄」 | 交易刪光之後就刪得掉 |
| 轉帳的「編輯」 | 不用改 | 舊的那筆直接移除，替換關係改記在稽核列 |
| 定存確認產生的交易 | 不用改 | 事件放手（`transaction_id` 設 NULL），維持已確認 |
| 交易紀錄頁 | 有「狀態」篩選與欄位 | 拿掉 |

**慣例。** 個人記帳軟體的主流是「確認後直接刪除」（常見的手機記帳 app、KMyMoney；GnuCash 的
「刪除交易」也是）。「作廢、紀錄留著」來自正式會計：公司的帳要接受稽核，已入帳的東西不能憑空消失；
開出去的支票作廢要留紀錄，跟銀行對帳才對得上。這類軟體（Quicken、QuickBooks、GnuCash）通常是
**刪除與作廢兩條路並存**，作廢給有那些需求的人用。這個專案只有作廢一條路 —— 等於把公司帳的規矩
套在一個人的帳本上。

使用者選了「一步到位真的刪除」：「我是認為確實刪除比較直觀。」

## 決定

**交易的「刪除」是真的移除。**

| 層 | 改了什麼 |
|---|---|
| store | `void_transaction()` → `delete_transaction()`。**移除一筆交易只有一個寫法** `StoreBase._remove_transaction()`：定存事件放手 → 刪 FTS、allocation、posting、交易 → 稽核 `transaction.delete`（流向與日期，**不記金額**） |
| 替換轉帳 | 建新的 ＋ `_remove_transaction(舊的)`，同一個 SQLite transaction。`replaces_transaction_id` **不再寫入** —— 它是指向舊交易的外鍵，會擋住刪除；替換關係改記在 `transaction.transfer_replace` 稽核列的 `replaces` |
| 定存 | 刪掉定存確認入帳產生的交易：`deposit_events.transaction_id` 設 NULL，事件**維持已確認** —— 跟以前作廢之後的結果一樣：那一筆待確認不會回來，錢也不算了。刪除確認框會先講這件事 |
| migration | `migrate_v13`：清掉 `replaces_transaction_id` → 指向已刪除交易的定存事件放手 → 刪已刪除交易的 FTS／allocation／posting／交易。它們本來就是使用者刪掉的（或是被替換掉的舊轉帳），不計入任何金額 —— 畫面上的數字不會變 |
| application／controller | `VoidTransaction` → `DeleteTransaction`；`TransactionFilter.status`、`RecordStatus.VOIDED` 拿掉；錯誤碼 TRANSACTION_VOIDED、TRANSFER_NOT_ACTIVE、TRANSACTION_STATUS_FILTER_INVALID 退役 |
| UI | 交易紀錄的「狀態」篩選與欄位拿掉；確認框念出是哪一筆、講刪掉之後只能從備份救，預設停在「否」 |
| CSV | 「狀態」欄拿掉 |

`status` 欄與它的 `CHECK` **留著**（同 ADR-0015：拿掉要重建整張表）。列表查詢裡的 `t.status = 'active'`
也留著 —— 那是讓 `(status, occurred_at)` 索引用得上的條件。`replaces_transaction_id` 欄同樣留著、不再寫；
`tests/unit/test_retired_schema_values.py` 守著「不再寫」。

## 被否決的替代方案

| 方案 | 為什麼否決 |
|---|---|
| **維持 `void`** | 使用者心裡的「刪除」就是沒了；只被已刪除交易用過的帳戶與類別永遠刪不掉 —— 跟 ADR-0015 修掉的是同一個形狀（看不見但還在） |
| **兩段式：維持 `void`，已刪除的再提供「永久刪除」** | 有拿出來比較（交易的作廢有一段反悔期的價值，這點跟盤點不同），使用者選了一步到位。真刪的代價（誤刪靠備份）由「確認框預設否 ＋ 念出是哪一筆」減輕 |
| **擋下定存產生的交易，不給刪** | 會拿走「撤回一筆確認錯的入帳」唯一的路 —— 以前那條路就是作廢它 |
| **刪掉定存交易時讓事件回到待確認** | 確認到期時已經把那一期結清或續存、開了下一期，那些退不回去。只對領息成立的規則，會讓兩種事件的行為不一樣 |
| **舊的 `voided` 留著讓使用者逐筆清** | 同 ADR-0015：它們已經被刪過一次了，要使用者再刪一次是讓舊做法的代價由使用者付 |

## 後果

- **好的**：「刪除」只剩一個意思 —— 交易、盤點、名冊都是真的移除；交易紀錄少一個篩選與一欄；
  只被刪掉的交易用過的帳戶與類別刪得掉。
- **壞的**：刪錯了就沒了，只能從備份救。確認框預設「否」（同一天修的，`widgets/confirm.py`）並念出是哪一筆。
- **稽核表仍然記得那筆交易的建立**（`transaction.create` 的 details 帶流向與金額）。畫面上看不到它；
  要連那些都抹掉，是另一個決定。
- **升級前要先手動備份**：`migrate_v13` 不能 un-delete，而程式依規定不自動備份。要改回來，是新增
  migration 與新的 ADR，不是改 `migrate_v13`。
- 「轉帳不能就地編輯、只能替換」不變（`TRANSFER_EDIT_NOT_SUPPORTED`）—— 替換現在是「建新的、刪舊的」。

## 什麼情況下這份 ADR 該被推翻

**帳本開始有稽核需求。** 例如要拿去報帳、跟別人共用，或需要證明「某一筆曾經記過又被刪掉」——
那時要的是 Quicken／GnuCash 那種「刪除與作廢並存」，而不是把刪除改回作廢。

# ADR-0010：對外轉帳記成收入／支出，不新增 entry_type

- 狀態：**已接受**
- 日期：2026-08-21
- 取代：無。與 [ADR-0006](ADR-0006-manual-entry-only.md) 一致，未推翻任何既有決定。

## 背景

改版前「轉帳」一定要兩個**自己建立的**帳戶（`stores/base.py` 的
`_require_active_account` 對來源與目的各檢查一次）。但實際生活裡的轉帳多半不是
自己兩個帳戶之間搬錢：房租匯給房東、薪水從公司匯進來、跟家人互相轉錢 ——
這些都是「轉帳」這個詞在使用者腦子裡的意思，而程式表達不了。

使用者的原話是「轉帳很多時候不是從自己建立的帳戶轉到自己建立的帳戶」。

## 決定

**畫面上「轉帳」底下多一排「轉帳對象」，但資料庫維持三種 `entry_type` 不變。**

| 轉帳對象 | 存成 | posting |
|---|---|---|
| 我的帳戶之間 | `entry_type = "transfer"` | 兩筆（來源負、目的正）|
| 別人轉入 | `entry_type = "income"` ＋ 類別／項目 | 一筆正 |
| 轉出給別人 | `entry_type = "expense"` ＋ 類別／項目 | 一筆負 |

判準是**總資產有沒有變**：錢真的離開或進入你的總資產時，那就是收支，不是轉帳。
這與 [`state-machines.md` §7](../architecture/state-machines.md) 已經寫下的
「**利息記成收入，不是轉帳**。利息是新產生的錢；只有本金在兩個帳戶之間移動才是轉帳」
是同一條原則的另一個應用。

程式**不自動建立任何類別**。建議的記法寫在
[`AGENTS.md`](../../AGENTS.md) 的「對外轉帳慣例」一節，形狀比照電子票證慣例。

## 被否決的方案

### 甲、新增 `transfer_in` / `transfer_out` 兩個 `entry_type`

看起來最直白，但代價分散在整個程式裡：

- 要一次 migration（`transactions.entry_type` 的 `CHECK` 約束）。
- **每一處加總都要重新確認**：總資產、餘額盤點的預期金額、未解釋差額、
  CSV 匯出、金額顏色（`amount_color`）、`signed_amount_text` 的正負號、
  待確認的分派、模板與定期收支的流向下拉。漏掉任何一處，症狀都是「數字不對」
  而不是「程式壞掉」—— 那是最難發現的一種錯。
- 而它們在帳本上的**效果與 income／expense 完全相同**。新增兩個語意重複的列舉值，
  換來的只是交易紀錄那一欄多兩個字。

`adjustment` 就是這個模式的前車之鑑：它從 v1 就在 `CHECK` 約束裡，
「為了將來的對帳調整」預留，至今（2026-08）沒有任何程式碼會建立它。
`state-machines.md` 把它明寫成「本專案『先加著以後再說』的實例，不是待辦事項」。

### 乙、建一個「外部」虛擬帳戶

轉出／轉入都指向它，維持兩筆 posting 的對稱。否決的理由是它會**外洩到每一個
用得到帳戶的地方**：帳戶清單、記帳頁的兩個下拉、交易紀錄的篩選、餘額盤點的帳戶選單、
定存的利息轉入帳戶。而「外部帳戶的餘額」是一個沒有意義的數字 —— 它會等於你這輩子
轉出給別人的錢減掉別人轉給你的錢，卻沒有任何一個地方該顯示它。

要擋住這些就得在每一處加一個「排除外部帳戶」的例外，而那份清單一定會漏。

## 後果

**好的：**

- 零 migration、零新列舉值。既有的加總、顏色、正負號全部照舊正確。
- 總資產一定對：對外轉帳讓它動，內部轉帳讓它不動。
- 「這筆是轉給誰的」用**類別／項目 ＋ 備註**表達，與 Phase 4 移除 payee 之後
  一貫的做法相同。

**要付的代價（知情且接受）：**

- 交易紀錄那一欄顯示的是「支出」或「收入」，不是「轉帳」。**這是誠實的** ——
  那筆錢真的離開了。要看出它是轉帳，靠的是類別／項目的名字。
- 使用者得自己建一個「轉帳」類別。程式在沒有任何類別時會提示去建，
  但**不會替他決定該叫什麼**。

## 怎麼推翻

如果日後真的需要在報表上把「對外轉帳」與一般收支分開統計，正確做法是新增一份 ADR
取代這一份，並且**同時**列出上面「方案甲」那張清單裡的每一處要怎麼改。
不要因為欄位加起來很快就先加。

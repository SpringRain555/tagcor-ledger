# ADR-0006 一律手動輸入

## 狀態

已接受（2026-08-18）。這是專案存在的理由，不是可調整的實作細節。

## 決策

每一筆帳都由使用者手動輸入。**不做**電子發票載具匯入、不做銀行同步、不做任何自動匯入，
排程與定存到期也只產生待確認項目、由使用者確認才入帳。

電子票證（悠遊卡／一卡通／iCash）**只記儲值當下的支出**，不建帳戶、不追蹤卡內餘額；
複數張卡共用同一個項目。

## 理由

手動輸入才讓使用者感受到花費的程度。自動歸戶把那個感受拿掉了 ——
卡片餘額自己會變，使用者不會經歷「我又花了 500」這個瞬間。

這與市場主流明確相反，而且是知情的。CWMoney 官網
（[money.cmoney.tw/cwmoney](https://money.cmoney.tw/cwmoney)，抓取 2026-08-18）的主打功能逐字是：

> 「歸戶悠遊卡、一卡通、iCash，同步雲端發票自動記帳，連帳戶都幫你分好了！」

Firefly III 也會自動建立週期交易，而且它的文件把定位講得很清楚：自動建立是
**匯入功能的替代品**，給沒有在匯入資料的人用的（[recurring](https://docs.firefly-iii.org/explanation/financial-concepts/recurring/)，抓取 2026-08-18）。
那解的是「我懶得輸入」，本專案解的是「我要感受到花費」，目的不同，不該照抄。

「只記儲值金額」在帳務上也是自洽的：儲值當下錢確實離開了郵局或現金，那一刻就是支出。
之後卡裡怎麼用，對「我這個月花了多少」不產生新資訊。

## 後果

- 看不出電子票證的消費結構。**這個代價是知情且接受的。**
- 不得為一卡通／悠遊卡建立帳戶或餘額欄位。這條要寫在 `AGENTS.md`，
  因為市面產品都這樣做，日後很容易有人「順手」加上去。
- 輸入摩擦是**核心風險**：輸入太麻煩使用者就會放棄記帳，而本專案沒有自動匯入當退路。
  降低摩擦的手法是 roadmap Phase 7 的主題，市場調查在這一塊的證據目前最弱
  （見 `docs/research/open-questions.md` Q2）。

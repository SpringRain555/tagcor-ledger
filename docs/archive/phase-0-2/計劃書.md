# TagCor Ledger 專案計劃書

## 0. 文件目的

本文件整理 TagCor Ledger 的產品目標、功能範圍、資料模型、系統架構、開發里程碑與品質標準。它同時修正既有草稿中敘述重複、策略前後不一致、驗收條件不足的問題，作為後續實作與評估進度的基準。

TagCor Ledger 是一個以「四層標籤」為核心的本機桌面記帳工具。第一階段以 Python + PyQt6 建立鍵盤優先的快速記帳體驗，資料先使用 CSV + JSON 儲存，並預留未來切換 SQLite 的介面。資料格式細節以 [資料格式規格.md](資料格式規格.md) 為準，模組邊界與階段實作以 [模組化與階段實作.md](模組化與階段實作.md) 為準。

## 1. 敘述完整性檢視

### 1.1 已補齊的缺口

1. **文件版本混雜**
   - 舊草稿同時出現「以標籤名稱寫入 CSV」與「以 Tag ID 寫入 ledger」兩種設計。
   - 修正：本文件統一採用 Tag ID 作為內部主鍵，名稱只作顯示與匯出用途。

2. **標籤改名策略不完整**
   - 舊草稿描述「改名時批次改 CSV」，但後續又提出「改名不重寫歷史資料」。
   - 修正：改名只更新 `tags.json`；ledger 以 ID 參照，不需要批次改名。只有合併、拆分、搬移需要 dry-run 與可回復的批次轉換。

3. **資料安全機制不足**
   - 舊草稿提到備份，但未定義觸發時機、命名、還原檢查與 audit。
   - 修正：補上原子寫入、自動備份、還原流程、三類 log 與 `correlation_id`。

4. **Use Case 與錯誤處理不明確**
   - 舊草稿提到 MVC，但缺少 UI 之外的應用層責任。
   - 修正：補上 Application Layer、統一 Result、錯誤碼、背景任務與可測試邊界。

5. **驗收標準不足**
   - 舊草稿列出功能，但缺少可判斷完成的條件。
   - 修正：每個 MVP 功能均補上驗收條件與測試策略。

6. **設定版本與遷移未落地**
   - 舊草稿提到 `schema_version`，但未定義啟動時行為。
   - 修正：啟動時必須驗證設定檔、備份舊檔、執行 migration，失敗時提供可理解錯誤與回復選項。

### 1.2 仍需在實作前確認的問題

1. **帳務語意**
   - L1 是否固定為 `收入 / 支出 / 轉帳 / 調整`，或允許使用者完全自訂。
   - 轉帳是否需要拆成兩筆交易，或以單筆交易記錄來源與目的帳戶。

2. **金額正負規則**
   - 支出是否以正數儲存、由 L1 決定方向，或直接儲存負數。
   - 建議第一期採「金額永遠為正，方向由 L1 決定」，降低輸入錯誤。

3. **資料儲存位置**
   - 預設放在專案資料夾、使用者文件資料夾，或作業系統 app data。
   - 建議 MVP 預設使用使用者文件資料夾下的 `TagCorLedger/`，並允許在設定中修改。

## 2. 產品目標與非目標

### 2.1 目標

1. **快速記帳**
   - 支援鍵盤優先操作。
   - 使用四層連動標籤快速選取分類。
   - 提供智慧樣板減少重複輸入。

2. **資料安全**
   - 所有檔案寫入採原子寫入。
   - 高風險操作前自動備份。
   - 支援基本還原流程。

3. **可追溯**
   - 使用 `app.log`、`error.log`、`audit.log` 分離記錄一般狀態、錯誤與使用者資料操作。
   - 每個 Use Case 產生 `correlation_id`，讓 UI 錯誤可對應到 log。

4. **可維護**
   - 採用 UI、Application、Domain、Infrastructure 分層。
   - Repository 介面先支援 CSV/JSON，未來可切換 SQLite。

5. **可遷移**
   - 設定檔與資料格式具備 `schema_version`。
   - 啟動時可檢查、升級、備份與回報錯誤。

### 2.2 非目標

- 第一階段不做多人協作與雲端同步。
- 第一階段不做手機端或網頁端。
- 第一階段不做完整會計系統，例如資產負債表、預算控制、稅務報表。
- 第一階段不做複雜報表，只提供最近交易、搜尋與基本匯出。

### 3.2 分層責任

MVP 階段採中等顆粒模組化。Use Case 先依主題分檔，例如 `transactions.py`、`tags.py`、`templates.py`、`maintenance.py`，不在第一版就拆成每個 Use Case 一個檔案。

#### App Layer

- 負責啟動流程、dependency wiring、使用者資料目錄、資源讀取與首次初始化。
- 保留未來打包成桌面應用程式的入口與路徑策略。
- 不包含帳務規則、CSV/JSON 實際讀寫或 PyQt 畫面細節。

#### UI Layer

- 使用 PyQt6 呈現視窗、表單、對話框與列表。
- 僅負責收集輸入、顯示結果、處理焦點與快捷鍵。
- 不直接讀寫 CSV/JSON。

#### Controller Responsibility

- Controller 放在 `ui/controllers.py`，接收 UI 事件。
- 將 UI 輸入轉成 Use Case request。
- 將 Use Case `Result` 轉成 UI 提示、列表刷新或錯誤訊息。

#### Application Layer

- 實作使用者操作流程。
- 負責驗證、鎖定、備份、呼叫 repository、寫 audit log、回傳 Result。
- 所有資料修改必須從 Use Case 進入。

#### Domain Layer

- 定義核心資料與規則。
- 包含 `Transaction`、`Money`、`TagNode`、`TagPath`、`Template`。
- 不依賴 PyQt、檔案系統或資料庫。

#### Infrastructure Layer

- 負責 CSV/JSON 讀寫、原子寫入、檔案鎖、備份、migration、logging。
- 對 Application 提供介面實作。
- 未來可在此層新增 SQLite repository。

## 4. 核心資料模型

本節只描述核心資料語意；欄位順序、格式限制、驗證規則與 migration 規則以 [資料格式規格.md](資料格式規格.md) 為準。

### 4.1 Transaction

交易紀錄使用 Tag ID 保存關聯，並同時保存 tag name snapshot，兼顧長期查詢與歷史語意。

```text
transaction_id: uuid
revision: integer
status: active | voided
entry_type: income | expense | transfer | adjustment
occurred_at: ISO 8601 datetime with timezone
recorded_at: ISO 8601 datetime with timezone
updated_at: ISO 8601 datetime with timezone
currency: ISO 4217
amount: decimal string
l1_id: string
l2_id: string
l3_id: string
l4_id: string
l1_name_snapshot: string
l2_name_snapshot: string
l3_name_snapshot: string
l4_name_snapshot: string
description: string
source: manual | template | import | migration
template_id: string | null
correlation_id: string
```

CSV 欄位建議：

```csv
schema_version,transaction_id,revision,status,entry_type,occurred_at,recorded_at,updated_at,currency,amount,l1_id,l2_id,l3_id,l4_id,l1_name_snapshot,l2_name_snapshot,l3_name_snapshot,l4_name_snapshot,description,source,template_id,correlation_id
```

規則：

- `amount` 一律為大於 0 的 Decimal 字串。
- 收入、支出、轉帳、調整由 `entry_type` 表示，不靠金額正負號。
- 編輯交易不建立新的 `transaction_id`，而是增加 `revision`。
- 刪除交易不實體刪除，改為 `status = voided`。
- 匯出時可選擇使用 current tag name 或 snapshot tag name。

### 4.2 Tag

Tag catalog 使用扁平陣列保存，透過 `parent_id` 與 `level` 表示四層關係，降低 migration 與改名維護成本。

```json
{
  "schema_version": 1,
  "levels": [
    { "level": 1, "code": "l1", "name": "流向", "required": true },
    { "level": 2, "code": "l2", "name": "帳戶", "required": true },
    { "level": 3, "code": "l3", "name": "分類", "required": true },
    { "level": 4, "code": "l4", "name": "細項", "required": true }
  ],
  "tags": [
    {
      "tag_id": "tag_expense",
      "parent_id": null,
      "level": 1,
      "name": "支出",
      "status": "active",
      "sort_order": 10,
      "aliases": [],
      "created_at": "2026-05-08T08:30:00+08:00",
      "updated_at": "2026-05-08T08:30:00+08:00",
      "archived_at": null
    },
    {
      "tag_id": "tag_cash",
      "parent_id": "tag_expense",
      "level": 2,
      "name": "現金",
      "status": "active",
      "sort_order": 10,
      "aliases": [],
      "created_at": "2026-05-08T08:30:00+08:00",
      "updated_at": "2026-05-08T08:30:00+08:00",
      "archived_at": null
    }
  ]
}
```

規則：

- 每個 tag 必須有穩定 ID。
- 同一父層底下 active tag 名稱不得重複。
- L1 到 L4 必須形成合法路徑。
- 改名不重寫 ledger。
- 已被 ledger 使用的 tag 不實體刪除，改為 `archived`。

### 4.3 Template

```json
{
  "schema_version": 1,
  "templates": [
    {
      "template_id": "tpl_breakfast",
      "name": "早餐",
      "status": "active",
      "l1_id": "tag_expense",
      "l2_id": "tag_cash",
      "l3_id": "tag_food",
      "l4_id": "tag_711",
      "default_amount": "0",
      "default_description": "",
      "focus_target": "amount",
      "sort_order": 10,
      "created_at": "2026-05-08T08:30:00+08:00",
      "updated_at": "2026-05-08T08:30:00+08:00",
      "archived_at": null
    }
  ]
}
```

規則：

- `default_amount` 使用字串保存 Decimal。
- `focus_target` 可為 `amount`、`description`、`submit`。
- 套用模板不自動送出。
- archived template 不顯示在快捷模板區。

```json
{

  "app_data_version": "1",
  "data_dir": "D:/Accounting/TagCorLedger",

  "export_dir": "D:/Accounting/TagCorLedger/exports",
  "log_dir": "D:/Accounting/TagCorLedger/logs",

  "default_currency": "TWD",

  "export_csv_encoding": "utf-8-sig"

```

### 4.5 Manifest

`data_manifest.json` 用於完整性檢查與外部修改偵測。它不是唯一資料來源，遺失時必須能重新掃描資料目錄產生。

```json
{
  "schema_version": 1,
  "generated_at": "2026-05-08T08:30:00+08:00",
  "files": [
    {
      "path": "data/ledger_2026.csv",
      "schema_version": 1,
      "sha256": "pending",
      "updated_at": "2026-05-08T08:30:00+08:00"
    }
  ]
}
```

規則：

- 寫入完成後更新 manifest。
- 啟動時若 manifest 與實際檔案不一致，提示使用者資料可能被外部修改。
- manifest 可重新產生，不應成為啟動單點失敗。

## 5. 核心流程

### 5.1 新增交易

1. UI 預設帶入目前日期與時間。
2. 使用者選擇 L1 至 L4。
3. 使用者輸入金額與描述。
4. 使用者按 Enter、`Ctrl+S` 或送出按鈕。
5. Controller 建立 `AddTransactionRequest`。
6. Use Case 驗證金額、時間、Tag path。
7. Use Case 解析 current tag name，建立 tag name snapshot。
8. Use Case 產生 `transaction_id` 與 `correlation_id`。
9. Repository 以原子寫入更新年度 ledger。
10. Audit log 記錄新增交易。
11. Manifest 更新檔案 checksum 與時間。
12. UI 清空表單並刷新最近交易。

驗收條件：

- 必填欄位缺漏時不可送出。
- 金額不得使用 float。
- 寫入成功後 CSV 有 Tag ID 與 tag name snapshot，audit log 有對應 correlation ID。
- 寫入失敗時 UI 顯示可理解錯誤，error log 有例外細節。

### 5.2 套用智慧樣板

1. 使用者點選模板或使用快捷鍵。
2. UI 套用模板中的 Tag IDs、預設金額與描述。
3. 系統依 `focus_target` 移動焦點。
4. 使用者仍需手動送出。

驗收條件：

- 套用模板後四層 tag path 合法。
- `default_amount = 0` 時焦點預設移到金額欄位。
- 不會因點選模板而直接寫入 ledger。

### 5.3 標籤改名

1. 使用者在標籤管理頁選取 tag。
2. 輸入新名稱。
3. Use Case 檢查同層不可重名。
4. 備份 `tags.json`。
5. 原子寫入新的 `tags.json`。
6. Audit log 記錄改名前後名稱與 tag ID。
7. UI 重新載入標籤顯示。

驗收條件：

- 改名不重寫 ledger。
- 歷史交易仍保留原本 snapshot；UI 可選擇顯示 current tag name 或 snapshot tag name。
- 同父層重名會被阻擋。

### 5.4 標籤合併或批次轉換

第一期可先不實作；若實作，必須符合以下流程：

1. 先 dry-run 顯示影響交易筆數與年份。
2. 建立完整備份。
3. 背景任務執行，提供進度與取消。
4. 完成後寫 audit log。
5. 失敗時提供還原選項。

## 6. UI 與操作設計

### 6.1 主視窗

主視窗建議分成四個區域：

1. **交易輸入區**
   - 日期、時間、L1、L2、L3、L4、金額、描述、送出。

2. **智慧樣板區**
   - 顯示常用模板按鈕。
   - 支援快捷鍵聚焦。

3. **最近交易列表**
   - 顯示最近新增紀錄。

   - 顯示資料位置、最近備份時間、錯誤 correlation ID。

### 6.2 鍵盤優先規則

Tab 順序：

```text
日期 -> 時間 -> L1 -> L2 -> L3 -> L4 -> 金額 -> 描述 -> 送出
```

- `Ctrl+S`：送出交易。
- `Ctrl+T`：聚焦模板區。
- `Ctrl+L`：聚焦 L1。
- `Esc`：清除目前表單。
- `F5`：重新載入資料。

## 7. Logging、Audit 與錯誤處理

### 7.1 Log 類型

- `app.log`：一般啟動、載入、設定、效能資訊。
- `error.log`：例外、堆疊、IO 失敗、migration 失敗。
- `audit.log`：新增、修改、刪除、改標籤、備份、還原、匯出。

### 7.2 Result 格式

Use Case 統一回傳：

```text
success: bool
error_code: string | null
message: string
details: dict
correlation_id: string
```

常見錯誤碼：

- `VALIDATION_REQUIRED_FIELD`
- `VALIDATION_INVALID_AMOUNT`
- `TAG_PATH_NOT_FOUND`
- `TAG_DUPLICATE_NAME`
- `FILE_LOCK_TIMEOUT`
- `FILE_READ_FAILED`
- `FILE_WRITE_FAILED`
- `MIGRATION_FAILED`
- `BACKUP_FAILED`

### 7.3 UI 錯誤顯示

UI 應顯示使用者能理解的訊息，例如：

```text
交易無法儲存：金額格式不正確。錯誤追蹤碼：01HX...
```

詳細堆疊只寫入 `error.log`，不直接顯示給使用者。

## 8. 檔案寫入、備份與還原

### 8.1 原子寫入

所有 JSON 與 CSV 寫入必須使用：

```text
寫入 .tmp -> flush/fsync -> os.replace
```

目的：

- 避免寫到一半中斷造成檔案毀損。
- 保證成功時完整替換，失敗時保留舊檔。

### 8.2 備份觸發時機

- App 啟動時每日一次備份。
- 高風險操作前必備份：
  - 標籤合併。
  - 批次轉換。
  - 還原。
  - migration。

### 8.3 備份命名

```text
YYYYMMDD_HHMMSS_tags.json.bak
YYYYMMDD_HHMMSS_templates.json.bak
YYYYMMDD_HHMMSS_ledger_2026.csv.bak
```

### 8.4 還原流程

1. 使用者選取備份。
2. 系統 dry-run 檢查檔案格式與 schema。
3. 顯示將還原的檔案與影響範圍。
4. 使用者確認。
5. 建立目前狀態備份。
6. 還原備份。
7. 寫 audit log。

## 9. Migration 策略

### 9.1 啟動流程

1. 讀取 settings、tags、templates。
2. 檢查 `schema_version`。
3. 若版本落後：
   - 先備份原檔。
   - 逐版執行 migration。
   - 驗證升級結果。
4. 若升級失敗：
   - 保留原檔。
   - 顯示錯誤與 correlation ID。
   - 提供開啟資料夾或還原選項。

### 9.2 Migration 原則

- migration 必須可測試。
- migration 不可直接修改原檔，必須透過備份與原子寫入。
- 不同 schema 版本的轉換需各自獨立，例如 `v1_to_v2.py`。

## 11. 測試策略

### 11.1 單元測試

- `Money`：Decimal 解析、格式錯誤、不可使用 float。
- `TagPath`：合法路徑、不完整路徑、不存在路徑。
- `Transaction`：必填欄位、timestamp、description。
- 資料格式 validator：settings/tags/templates/ledger row。
- Use Case：成功、驗證失敗、repository 例外。
- Migration：舊 schema 到新 schema。

### 11.2 整合測試

- CSV repository 寫入與讀取。
- JSON repository 原子寫入。
- Backup/restore 一致性。
- Audit log 是否產生必要欄位。
- Tag ID 與 tag name snapshot 寫入策略正確。
- Manifest 可重新產生並偵測外部修改。

### 11.3 UI 測試

- Tab 順序。
- 快捷鍵。
- Cascading ComboBox 連動。
- 套用模板後焦點位置。

## 12. 開發規範

1. 金額一律使用 `Decimal`，禁止 float。
2. 資料修改一律經過 Application Use Case。
3. UI 不可直接讀寫 repository。
4. 所有檔案寫入使用 atomic writer。
5. 所有使用者資料操作寫 audit log。
6. 長任務必須背景化，並提供進度與取消。
7. 錯誤回傳必須包含 `correlation_id`。
8. 新增資料格式時必須同步更新 schema 與 migration。
9. ledger 必須同時保存 Tag ID 與 tag name snapshot。
10. 已使用 tag 與交易不得實體刪除，必須使用 archived/voided 狀態。
11. 文件、範例檔與測試需隨功能一起更新。

## 13. 第一階段完成定義

第一階段完成時，應具備以下能力：

- 使用者可以用鍵盤快速新增交易。
- 交易以 Tag ID 與 tag name snapshot 寫入 CSV。
- 標籤可以改名且歷史資料不需重寫，歷史 snapshot 不被覆蓋。
- 智慧樣板可以套用但不自動送出。
- 錯誤可追蹤到 `correlation_id`。
- 啟動、寫入、備份、還原都有 log 與 manifest 更新。
- 設定檔有 `schema_version` 並可 migration。
- MVP 功能具備單元測試與關鍵整合測試。

# TagCor Ledger 資料格式規格

## 0. 文件目的

本文件定義 TagCor Ledger 第一階段的 canonical data format。目標是讓資料可長時間保存、容易備份、容易檢查、容易 migration，並在未來切換 SQLite 時不需要重新定義核心資料語意。

本規格優先滿足以下需求：

1. **長期可讀**
   - 使用 CSV + JSON 作為第一階段儲存格式。
   - 避免私有二進位格式。
   - 人類可以直接打開檢查資料。

2. **長期可信**
   - ledger 同時保存 Tag ID 與 tag name snapshot。
   - 改名不破壞關聯，也不抹除交易發生當下的文字語意。
   - 所有資料變更透過 audit log 追蹤。

3. **低維護成本**
   - JSON 使用扁平結構，降低樹狀遞迴更新與 migration 成本。
   - CSV 欄位固定且版本化。
   - 檔案寫入統一走 atomic writer。

4. **可演進**
   - 每種資料格式具備 `schema_version`。
   - migration 必須逐版執行。
   - 欄位命名盡量能直接映射到未來 SQLite table。

## 1. 儲存目錄結構

預設資料目錄建議為使用者文件資料夾下的 `TagCorLedger/`，實際位置可由 `settings.json` 指定。

```text
TagCorLedger/
├── config/
│   ├── settings.json
│   ├── tags.json
│   ├── templates.json
│   └── data_manifest.json
├── data/
│   ├── ledger_2026.csv
│   └── ledger_2027.csv
├── backups/
│   └── 20260508_083000/
│       ├── backup_manifest.json
│       ├── settings.json.bak
│       ├── tags.json.bak
│       ├── templates.json.bak
│       └── ledger_2026.csv.bak
├── exports/
├── logs/
│   ├── app.log
│   ├── error.log
│   └── audit.log
└── tmp/
```

規則：

- `config/`、`data/` 是 canonical data。
- `exports/` 是衍生資料，不可視為唯一備份。
- `logs/audit.log` 是資料操作追蹤來源，採 JSON Lines。
- `data_manifest.json` 用於完整性檢查與外部修改偵測，但必須可以重新產生。
- `tmp/` 僅供 atomic writer 與背景任務暫存，啟動時可安全清理過期檔。

## 2. 通用格式規則

### 2.1 編碼與換行

- JSON 與 canonical CSV 使用 UTF-8。
- JSON 寫入時使用 `ensure_ascii=false` 與 2 spaces indent。
- CSV 使用 Python `csv` module 讀寫，不手刻逗號分割。
- canonical CSV 建議使用 CRLF line ending，以貼近 RFC 4180 與 Windows 工具相容性。
- 匯出給 Excel 的 CSV 可使用 UTF-8 BOM；canonical CSV 不依賴 BOM。

### 2.2 時間格式

所有時間欄位使用 ISO 8601，且必須包含 timezone offset。

```text
2026-05-08T08:30:00+08:00
```

規則：

- 不接受無 timezone 的時間。
- 不以本機 locale 字串保存，例如 `2026/5/8 上午 8:30`。
- `occurred_at` 表示交易實際發生時間。
- `recorded_at` 表示使用者建立紀錄時間。
- `updated_at` 表示最後修改時間。

### 2.3 金額格式

金額以 Decimal 字串保存。

```text
120
120.5
120.50
```

規則：

- 禁止 float。
- 禁止科學記號，例如 `1e3`。
- 禁止千分位逗號，例如 `1,200`。
- ledger 的 `amount` 必須大於 0。
- 正負方向不寫入 `amount`，由 `entry_type` 表示。
- template 的 `default_amount` 可為 `"0"`，代表套用模板後仍需使用者輸入。

### 2.4 ID 格式

建議使用帶前綴的 UUID hex 字串。

```text
txn_5c3d0d1a0d3f4e66b0c8b2abf9d5431a
tag_8d6e2b3f7a2a4d4a9d6a09b2b0a31d9f
tpl_b88d9556de2f4429a4be84be0692e60d
```

規則：

- ID 一旦建立不得因改名、搬移、排序而改變。
- 不使用顯示名稱產生 ID。
- 不在 ID 中保存使用者隱私或業務語意。

### 2.5 狀態欄位

狀態欄位使用固定小寫 enum。

- tag status：`active`、`archived`
- transaction status：`active`、`voided`
- template status：`active`、`archived`

規則：

- 已被 ledger 使用的 tag 不做實體刪除，改用 `archived`。
- ledger 交易不做實體刪除，改用 `voided`。

## 3. settings.json

### 3.1 用途

保存應用程式層級設定。它不保存交易資料，也不保存 tag tree。

### 3.2 Schema

```json
{
  "schema_version": 1,
  "app_data_version": "1",
  "data_dir": "D:/Accounting/TagCorLedger",
  "config_dir": "D:/Accounting/TagCorLedger/config",
  "ledger_dir": "D:/Accounting/TagCorLedger/data",
  "backup_dir": "D:/Accounting/TagCorLedger/backups",
  "export_dir": "D:/Accounting/TagCorLedger/exports",
  "log_dir": "D:/Accounting/TagCorLedger/logs",
  "timezone": "Asia/Taipei",
  "default_currency": "TWD",
  "startup_backup": "daily",
  "export_csv_encoding": "utf-8-sig",
  "created_at": "2026-05-08T08:30:00+08:00",
  "updated_at": "2026-05-08T08:30:00+08:00"
}
```

### 3.3 欄位規則

| 欄位 | 必填 | 說明 |
|---|---:|---|
| `schema_version` | 是 | 設定檔 schema 版本。 |
| `app_data_version` | 是 | 整體資料格式版本，第一版為 `"1"`。 |
| `data_dir` | 是 | 使用者資料根目錄。 |
| `config_dir` | 是 | JSON 設定檔目錄。 |
| `ledger_dir` | 是 | 年度 ledger CSV 目錄。 |
| `backup_dir` | 是 | 備份目錄。 |
| `export_dir` | 是 | 匯出目錄。 |
| `log_dir` | 是 | log 目錄。 |
| `timezone` | 是 | 預設時區。 |
| `default_currency` | 是 | 預設幣別，使用 ISO 4217，例如 `TWD`。 |
| `startup_backup` | 是 | `never`、`daily`、`always`。 |
| `export_csv_encoding` | 是 | 匯出 CSV 編碼，預設 `utf-8-sig`。 |

## 4. tags.json

### 4.1 用途

保存目前可用的 tag catalog。第一階段使用四層標籤，但資料格式保留 `level`，避免未來規格調整時必須重寫整個檔案。

### 4.2 設計原則

- 使用扁平陣列，不使用深層 nested tree。
- `parent_id` 表示階層關係。
- `level` 明確標示 L1 至 L4。
- `sort_order` 控制 UI 顯示順序。
- 改名只更新 `name`，不修改 ledger。
- 已使用 tag 不刪除，只封存。

### 4.3 Schema

```json
{
  "schema_version": 1,
  "levels": [
    {
      "level": 1,
      "code": "l1",
      "name": "流向",
      "required": true
    },
    {
      "level": 2,
      "code": "l2",
      "name": "帳戶",
      "required": true
    },
    {
      "level": 3,
      "code": "l3",
      "name": "分類",
      "required": true
    },
    {
      "level": 4,
      "code": "l4",
      "name": "細項",
      "required": true
    }
  ],
  "tags": [
    {
      "tag_id": "tag_expense",
      "parent_id": null,
      "level": 1,
      "name": "支出",
      "status": "active",
      "sort_order": 10,
      "aliases": [],
      "created_at": "2026-05-08T08:30:00+08:00",
      "updated_at": "2026-05-08T08:30:00+08:00",
      "archived_at": null
    },
    {
      "tag_id": "tag_cash",
      "parent_id": "tag_expense",
      "level": 2,
      "name": "現金",
      "status": "active",
      "sort_order": 10,
      "aliases": [],
      "created_at": "2026-05-08T08:30:00+08:00",
      "updated_at": "2026-05-08T08:30:00+08:00",
      "archived_at": null
    }
  ]
}
```

### 4.4 驗證規則

1. `tag_id` 必須唯一。
2. `parent_id = null` 時，`level` 必須為 1。
3. `level > 1` 時，`parent_id` 必須存在且父層 `level = child.level - 1`。
4. 同一個 `parent_id` 底下，active tag 的 `name` 不得重複。
5. `status = archived` 時，`archived_at` 必須有值。
6. archived tag 不出現在新增交易的下拉選單，但歷史交易仍可解析。
7. `aliases` 僅供搜尋與輔助顯示，不可作為主鍵。

## 5. templates.json

### 5.1 用途

保存智慧樣板，用於快速帶入 tag path、預設金額、描述與焦點行為。

### 5.2 Schema

```json
{
  "schema_version": 1,
  "templates": [
    {
      "template_id": "tpl_breakfast",
      "name": "早餐",
      "status": "active",
      "l1_id": "tag_expense",
      "l2_id": "tag_cash",
      "l3_id": "tag_food",
      "l4_id": "tag_711",
      "default_amount": "0",
      "default_description": "",
      "focus_target": "amount",
      "sort_order": 10,
      "created_at": "2026-05-08T08:30:00+08:00",
      "updated_at": "2026-05-08T08:30:00+08:00",
      "archived_at": null
    }
  ]
}
```

### 5.3 驗證規則

1. `template_id` 必須唯一。
2. `l1_id` 至 `l4_id` 必須形成合法且 active 的 tag path。
3. `default_amount` 必須是 Decimal 字串，可為 `"0"`。
4. `focus_target` 只能是 `amount`、`description`、`submit`。
5. archived template 不顯示在快捷模板區，但可保留供 audit 或還原參考。

## 6. 年度 ledger CSV

### 6.1 用途

保存交易目前狀態。每年一個檔案，檔名以 `occurred_at` 的年份決定。

```text
data/ledger_2026.csv
```

### 6.2 欄位順序

canonical CSV 欄位順序固定如下：

```csv
schema_version,transaction_id,revision,status,entry_type,occurred_at,recorded_at,updated_at,currency,amount,l1_id,l2_id,l3_id,l4_id,l1_name_snapshot,l2_name_snapshot,l3_name_snapshot,l4_name_snapshot,description,source,template_id,correlation_id
```

### 6.3 欄位說明

| 欄位 | 必填 | 說明 |
|---|---:|---|
| `schema_version` | 是 | ledger row schema 版本，第一版為 `1`。 |
| `transaction_id` | 是 | 交易穩定 ID。 |
| `revision` | 是 | 交易修訂次數，建立時為 `1`。 |
| `status` | 是 | `active` 或 `voided`。 |
| `entry_type` | 是 | `income`、`expense`、`transfer`、`adjustment`。 |
| `occurred_at` | 是 | 交易發生時間。 |
| `recorded_at` | 是 | 建立紀錄時間。 |
| `updated_at` | 是 | 最後修改時間。 |
| `currency` | 是 | ISO 4217，例如 `TWD`。 |
| `amount` | 是 | 大於 0 的 Decimal 字串。 |
| `l1_id` | 是 | L1 Tag ID。 |
| `l2_id` | 是 | L2 Tag ID。 |
| `l3_id` | 是 | L3 Tag ID。 |
| `l4_id` | 是 | L4 Tag ID。 |
| `l1_name_snapshot` | 是 | 建立或最後一次重分類時的 L1 顯示名稱。 |
| `l2_name_snapshot` | 是 | 建立或最後一次重分類時的 L2 顯示名稱。 |
| `l3_name_snapshot` | 是 | 建立或最後一次重分類時的 L3 顯示名稱。 |
| `l4_name_snapshot` | 是 | 建立或最後一次重分類時的 L4 顯示名稱。 |
| `description` | 否 | 使用者備註。 |
| `source` | 是 | `manual`、`template`、`import`、`migration`。 |
| `template_id` | 否 | 若由 template 建立，保存 template ID。 |
| `correlation_id` | 是 | 對應 audit/error log 的追蹤 ID。 |

### 6.4 範例

```csv
schema_version,transaction_id,revision,status,entry_type,occurred_at,recorded_at,updated_at,currency,amount,l1_id,l2_id,l3_id,l4_id,l1_name_snapshot,l2_name_snapshot,l3_name_snapshot,l4_name_snapshot,description,source,template_id,correlation_id
1,txn_5c3d0d1a0d3f4e66b0c8b2abf9d5431a,1,active,expense,2026-05-08T08:30:00+08:00,2026-05-08T08:31:00+08:00,2026-05-08T08:31:00+08:00,TWD,85,tag_expense,tag_cash,tag_food,tag_711,支出,現金,伙食,7-11,早餐,template,tpl_breakfast,corr_5f03a3dd2b8740198365bd7e4ab6d2d3
```

### 6.5 Snapshot 規則

ledger 必須同時保存 Tag ID 與 tag name snapshot。

目的：

- Tag ID 用於關聯、查詢、合併與未來 SQLite migration。
- Snapshot 用於保存交易當下的語意。
- 匯出時可選擇使用 current tag name 或 snapshot tag name。

規則：

1. 新增交易時，snapshot 取當下 tag name。
2. 單純 tag 改名時，不重寫 ledger snapshot。
3. 交易重分類時，更新 tag IDs 與 snapshot，並增加 `revision`。
4. 批次 tag 合併時，是否更新 snapshot 必須由 dry-run 顯示並要求使用者確認。

### 6.6 編輯與刪除規則

1. 編輯交易時更新同一列，不建立新的 `transaction_id`。
2. `revision` 必須加 1。
3. `updated_at` 必須更新。
4. 任何欄位改變都必須寫 audit log，包含 before/after。
5. 刪除交易不得實體刪除列，改為 `status = voided`。
6. `voided` 交易預設不計入統計，但仍可在 UI 中顯示或還原。

### 6.7 年度檔案規則

1. 檔案年份由 `occurred_at` 決定。
2. 若編輯交易導致 `occurred_at` 跨年，必須在備份後將該列移到新的年度檔案。
3. 跨年移動必須寫 audit log。
4. 匯總查詢需支援跨年度讀取，並以背景任務執行。

## 7. data_manifest.json

### 7.1 用途

`data_manifest.json` 用於快速檢查資料目錄完整性、偵測外部修改、輔助備份與還原。它不是唯一真相來源，遺失時必須能重新掃描資料目錄產生。

### 7.2 Schema

```json
{
  "schema_version": 1,
  "generated_at": "2026-05-08T08:30:00+08:00",
  "files": [
    {
      "path": "config/settings.json",
      "schema_version": 1,
      "sha256": "pending",
      "updated_at": "2026-05-08T08:30:00+08:00"
    },
    {
      "path": "data/ledger_2026.csv",
      "schema_version": 1,
      "sha256": "pending",
      "updated_at": "2026-05-08T08:30:00+08:00"
    }
  ]
}
```

規則：

- `sha256` 在寫入完成後計算。
- 若 manifest 與實際檔案不一致，啟動時應提示使用者資料可能被外部修改。
- 使用者仍可選擇重新索引，不應直接阻擋啟動。

## 8. audit.log

### 8.1 格式

`audit.log` 使用 JSON Lines，每一行是一個 JSON object。

### 8.2 Schema

```json
{
  "schema_version": 1,
  "audit_id": "aud_0f4df5e3d8f14ac8b7f7e8fc9f7731d4",
  "occurred_at": "2026-05-08T08:30:00+08:00",
  "correlation_id": "corr_5f03a3dd2b8740198365bd7e4ab6d2d3",
  "actor": "local_user",
  "action": "transaction.create",
  "entity_type": "transaction",
  "entity_id": "txn_5c3d0d1a0d3f4e66b0c8b2abf9d5431a",
  "result": "success",
  "details": {
    "ledger_file": "data/ledger_2026.csv"
  }
}
```

### 8.3 Action 命名

建議格式：

```text
transaction.create
transaction.update
transaction.void
tag.rename
tag.archive
template.create
template.update
backup.create
restore.apply
migration.apply
export.create
```

規則：

- audit log 不保存密碼或敏感 token。
- 資料修改失敗也應寫 audit，`result` 使用 `failure`。
- UI 顯示錯誤時顯示 `correlation_id`，方便追查 audit 與 error log。

## 9. 備份格式

### 9.1 備份目錄

每次備份建立獨立資料夾。

```text
backups/20260508_083000/
```

### 9.2 backup_manifest.json

```json
{
  "schema_version": 1,
  "backup_id": "bak_20260508_083000",
  "created_at": "2026-05-08T08:30:00+08:00",
  "reason": "before_migration",
  "correlation_id": "corr_5f03a3dd2b8740198365bd7e4ab6d2d3",
  "files": [
    {
      "source_path": "config/tags.json",
      "backup_path": "tags.json.bak",
      "sha256": "pending"
    }
  ]
}
```

規則：

- 還原前必須驗證 `backup_manifest.json`。
- 還原前必須先備份目前狀態。
- 還原動作必須寫 audit log。

## 10. Migration 規則

### 10.1 版本策略

- JSON 檔案使用檔案層級 `schema_version`。
- ledger CSV 使用 row-level `schema_version`。
- migration 只能逐版執行，例如 v1 -> v2 -> v3。
- 不允許跳版直接轉換。

### 10.2 寫入策略

每次 migration：

1. 驗證來源格式。
2. 建立備份。
3. 產生新檔到 `tmp/`。
4. 驗證新檔。
5. 使用 atomic replace。
6. 更新 manifest。
7. 寫 audit log。

### 10.3 相容性規則

- 新增非必填欄位：允許 minor migration。
- 新增必填欄位：必須提供預設值或轉換規則。
- 改名欄位：必須保留 migration。
- 刪除欄位：至少保留一版 migration 與備份提示。
- 改變欄位語意：必須更新資料格式規格與測試 fixtures。

---

## 11. SQLite 對應策略

第一階段雖然使用 CSV + JSON，但欄位命名要能直接映射到 SQLite：

| CSV/JSON | 未來 SQLite table |
|---|---|
| `ledger_YYYY.csv` | `transactions` |
| `tags.json.tags` | `tags` |
| `templates.json.templates` | `templates` |
| `settings.json` | `settings` |
| `audit.log` | `audit_events` |

SQLite migration 時：

- `transaction_id`、`tag_id`、`template_id` 保持不變。
- `*_name_snapshot` 匯入 `transactions` table。
- `status`、`revision`、`created_at`、`updated_at` 保持欄位語意。
- 匯入後仍保留原 CSV/JSON 備份。

## 12. 驗收條件

資料格式實作完成時，至少必須通過以下驗收：

1. `settings.json`、`tags.json`、`templates.json` 能通過 schema 驗證。
2. 新增交易會同時寫入 Tag ID 與 tag name snapshot。
3. 單純 tag 改名不會重寫 ledger。
4. 改名後，交易查詢可選擇顯示 current tag name 或 snapshot tag name。
5. `amount` 使用 Decimal 字串，且不接受 float、科學記號或千分位逗號。
6. `occurred_at`、`recorded_at`、`updated_at` 都包含 timezone。
7. 編輯交易會增加 `revision` 並寫 audit log。
8. 刪除交易只會 void，不會實體刪除列。
9. 每次 high-risk operation 前會建立備份。
10. manifest 可重新產生，且能偵測檔案變更。

## 13. 實作優先順序

MVP 建議依序實作：

1. `settings.json`、`tags.json`、`templates.json` 的 dataclass / validator。
2. CSV ledger reader/writer，先支援新增交易。
3. Tag path resolver，能從 ID 取得 current name 與 snapshot。
4. Atomic writer。
5. Audit JSON Lines writer。
6. Backup service。
7. Manifest generator。
8. Migration runner。

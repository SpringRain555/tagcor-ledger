# TagCor Ledger 模組化與階段實作規劃

## 0. 文件目的

本文件定義 TagCor Ledger 在開始實作前的模組邊界與階段性開發內容。目標是保留擴展性、降低長期維護成本，並避免在 MVP 階段過度拆分。

本專案適合模組化，但不適合一開始就切得太細。第一階段應以「責任清楚、檔案數可控、容易測試」為原則，等某個模組變大或責任變多時再拆分。

---

## 1. 模組化原則

### 1.1 切分原則

1. **依責任切分，不依畫面切分**
   - 資料規則、使用者流程、檔案存取、UI 顯示要分開。
   - 不讓 UI 直接讀寫 CSV/JSON。

2. **MVP 先採中等顆粒**
   - 不為每個按鈕、每個小功能建立獨立檔案。
   - 相近 Use Case 可先放在同一個模組，例如交易 command/query、tag/template 管理。

3. **先穩定資料契約**
   - `docs/資料格式規格.md` 是資料格式依據。
   - 先讓資料模型、validator、repository 邊界穩定，再接 UI。

4. **讓未來打包成應用程式不用重構**
   - 啟動入口、資源讀取、使用者資料目錄、設定初始化要獨立。
   - 不把檔案路徑寫死在 UI 或 domain。

5. **以測試邊界檢查模組邊界**
   - Domain 與 Application 應可在不啟動 PyQt 的情況下測試。
   - Infrastructure 可用臨時資料夾測試。

### 1.2 不做的過度拆分

MVP 階段暫時不做：

- 每個 Use Case 都獨立一個檔案。
- 每個 UI widget 都獨立一個資料夾。
- 先抽象出多資料庫框架。
- 先做 plugin 系統。
- 先把所有設定做成複雜 DI container。

## 3. 模組責任

### 3.1 `app/`

負責應用程式啟動與執行環境。

包含：

- 啟動流程與 dependency wiring。
- 使用者資料目錄解析。
- 首次啟動初始化。
- packaged app 與開發模式的資源讀取差異。

不包含：

- 帳務規則。
- CSV/JSON 實際讀寫。
- PyQt 畫面細節。

### 3.2 `domain/`

負責純業務模型與規則。

包含：

- `Money` Decimal 規則。
- `Transaction`、`Tag`、`Template` 等資料模型。
- Tag path 驗證。
- 時間、狀態、ID、金額格式驗證。

不包含：

- 檔案路徑。
- PyQt。
- log 寫入。

### 3.3 `application/`

負責使用者操作流程。

包含：

- `transactions.py`：新增、查詢、編輯、void 交易。
- `tags.py`：標籤改名、封存、合法路徑查詢。
- `templates.py`：模板 CRUD 與套用。
- `maintenance.py`：備份、還原、manifest、migration、匯出。
- 統一 `Result`。

不包含：

- 直接操作 PyQt widget。
- 手刻 CSV/JSON。

### 3.4 `infrastructure/`

負責外部世界與資料保存。

包含：

- CSV ledger repository。
- JSON config repository。
- atomic writer、file lock、backup。
- audit log、manifest。
- migration runner。

不包含：

- UI 呈現。
- 業務規則決策。

### 3.5 `ui/`

負責 PyQt6 使用者介面。

包含：

- 主視窗。
- 交易輸入面板。
- 最近交易列表。
- 標籤與模板管理對話框。
- UI controller，將畫面事件轉成 application request。

不包含：

- 直接讀寫 CSV/JSON。
- 金額與 tag path 的最終業務驗證。

### 3.6 `resources/`

負責打包時也需要帶上的靜態資源。

包含：

- QSS。
- icon。
- 預設圖片或 UI 資源。

規則：

- 程式讀取資源時應使用 `importlib.resources`。
- 不使用相對目前工作目錄的硬編路徑。

## 4. 模組依賴方向

依賴方向必須保持單向：

```text
ui -> application -> domain
ui -> application -> infrastructure
app -> ui/application/infrastructure
infrastructure -> domain
```

禁止：

```text
domain -> infrastructure
domain -> ui
application -> ui
infrastructure -> ui
```

說明：

- `domain` 是最穩定的核心，不知道 UI 與檔案系統存在。
- `application` 可以呼叫 repository 介面，但不關心 CSV/JSON 細節。
- `ui` 只透過 application 執行資料操作。
- `app` 負責組裝實際依賴，例如把 CSV repository 注入 Use Case。

---

## 5. 打包應用程式的保留空間

為了未來不重構即可包裝成桌面應用，實作時需保留：

1. **明確入口**
   - `src/tagcor_ledger/main.py`：GUI 啟動。
   - `src/tagcor_ledger/__main__.py`：支援 `python -m tagcor_ledger`。
   - `pyproject.toml`：定義 entry point。

2. **資源讀取抽象**
   - QSS、icon 不用硬編相對路徑。
   - 使用 `importlib.resources`。

3. **使用者資料目錄**
   - 使用 `platformdirs` 取得 app data path。
   - 不把使用者資料寫到安裝目錄。

4. **開發模式與打包模式一致**
   - app 啟動時透過同一組 `paths.py` 取得 config/data/log/backup 位置。
   - 測試可用 temporary data dir 注入。

5. **打包工具不進入 MVP 主線**
   - MVP 不急著產生 installer。
   - 先確保入口、資源、資料路徑正確，之後再補 PyInstaller/Nuitka 規格。

## 6. 階段性實作內容

以下階段刻意保持 5 個大階段，避免切成太多微任務。

### Phase 0：專案骨架與可打包入口

目標：

- 建立可安裝、可測試、可啟動的 Python package 骨架。

交付內容：

- `pyproject.toml`
- `src/tagcor_ledger/__init__.py`
- `src/tagcor_ledger/__main__.py`
- `src/tagcor_ledger/main.py`
- `app/paths.py`、`app/resources.py`、`app/bootstrap.py`
- 基本測試設定。

驗收條件：

- `python -m tagcor_ledger` 可啟動最小 app 或顯示啟動流程。
- 測試可執行。
- resources 與 data path 不依賴目前工作目錄。

### Phase 1：資料核心與基礎設施

目標：

- 先讓資料模型、格式驗證、檔案寫入、audit、manifest 穩定。

交付內容：

- Domain models 與 validators。
- `settings/tags/templates/ledger row` validator。
- CSV/JSON repository 初版。
- Atomic writer。
- Audit JSON Lines writer。
- Manifest generator。
- 範例資料。

驗收條件：

- 範例資料可通過驗證。
- 可在 temporary data dir 建立初始資料。
- 可原子寫入 JSON 與 ledger CSV。
- 寫入後 manifest 可更新。

### Phase 2：交易主線 MVP

目標：

- 完成最重要的記帳閉環。

交付內容：

- `AddTransaction`
- `ListRecentTransactions`
- Tag path resolver。
- Snapshot 建立策略。
- 最小 PyQt 主視窗與交易輸入面板。
- 最近交易列表。

驗收條件：

- 使用者可新增一筆交易。
- ledger row 包含 Tag ID、tag name snapshot、revision、status、correlation ID。
- audit log 有新增紀錄。
- 鍵盤 Tab 順序與 `Ctrl+S` 可用。

### Phase 3：管理功能與安全操作

目標：

- 補齊日常維護能力，避免資料越用越難整理。

交付內容：

- 標籤改名與封存。
- 模板 CRUD 與套用。
- 交易編輯與 void。
- Backup/restore 基本版。
- Migration runner v1。

驗收條件：

- Tag 改名不重寫 ledger snapshot。
- 已使用 tag 不可實體刪除，只能 archived。
- 交易刪除使用 voided。
- 高風險操作前自動備份。
- 還原前會驗證 backup manifest。

### Phase 4：查詢、匯出與發布準備

目標：

- 讓 MVP 變成可長期使用、可交付的桌面工具。

交付內容：

- 日期、tag、描述關鍵字查詢。
- 匯出 CSV，可選 current tag name 或 snapshot tag name。
- Log viewer 或 correlation ID 輔助查找。
- 打包發布規格文件。
- PyInstaller 或 Nuitka 初版設定。

驗收條件：

- 可跨年度查詢且 UI 不凍結。
- 匯出結果可被 Excel/LibreOffice 正常開啟。
- 打包後資源、資料目錄、log 位置正確。
- 開發模式與打包模式共用同一套啟動邏輯。

## 7. 拆分時機

以下情況才需要進一步拆模組：

1. 單一檔案超過約 400 至 500 行，且包含兩種以上責任。
2. 某個模組的測試需要大量 unrelated fixtures。
3. 新增功能時常常修改同一個大型檔案的不同區域。
4. CSV repository 與未來 SQLite repository 開始共存。
5. UI 對話框數量明顯增加。

拆分方向：

- `application/transactions.py` 可拆成 `transaction_commands.py` 與 `transaction_queries.py`。
- `infrastructure/repositories.py` 可拆成 repository protocols 與具體實作。
- `ui/management_dialogs.py` 可拆成 tag/template/backup 各自 dialog。

## 8. 模組化的優缺點

### 8.1 優點

- 降低長期維護成本。
- Domain 與 Application 可不用啟動 UI 就測試。
- 未來 CSV 換 SQLite 時，主要改 infrastructure。
- 未來打包成桌面應用時，入口與資源路徑已經清楚。
- 新功能可以沿既有邊界增加，不需要推翻架構。

### 8.2 缺點

- 初期檔案數比單檔程式多。
- 小功能可能需要同時改 UI、Application、Infrastructure。
- 需要維持邊界紀律，尤其不能讓 UI 直接讀寫資料檔。
- 若過早拆太細，會增加搜尋與理解成本。

### 8.3 本專案採取的折衷

- 先用 5 個主要模組：`app`、`domain`、`application`、`infrastructure`、`ui`。
- Use Case 先依主題分檔，不每個 use case 一檔。
- UI 先依主畫面/管理對話框分檔，不每個 widget 一檔。
- 資料格式與 migration 先嚴謹，因為這是長期帳本最難回頭修改的地方。
